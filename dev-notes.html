把一塊 2016 年的 OpenWrt 板子養成能用的開發環境

從把根檔案系統搬上 SD 卡開始:裝現代 Python、修好一個把整個區網打趴的 L2 迴圈、寫一個 MCP server 讓 AI 直接操作板上硬體,最後喚醒板上 第二顆晶片提供類比輸入。過程中撞到的每一個坑、每一個自己製造的假訊號、 每一個還沒解決的問題,都記錄在這裡。

三層根因,不是一個

最初的症狀是 ls /Media/SD-P1 回報 Too many levels of symbolic links —— 一個完全誤導的訊息, 它只是 autofs 掛載失敗後留下的懸空 symlink。往下每挖一層,才露出真正的原因。

層 1 · 分割區類型 0x83

卡是 ext4,但核心不認得 ext4

MBR 偏移 450 的類型位元組是 0x83(Linux),superblock 偏移 1080 的 magic 是 53 ef。但 /proc/filesystems 只有 squashfs、jffs2、overlay、exfat、vfat。 

# mount -t ext4 /dev/mmcblk0p1 /mnt/sd
failed: No such device   ← 核心根本沒有 ext4 這個 fs type
層 2 · metadata_csum

裝完 ext4 後,mount 改成「無回應」

現代 mkfs.ext4 預設啟用 metadata_csum,掛載時需要 crc32c, 而 kmod-fs-ext4 不會把它拉進來。核心卡在 request_module("crc32c") 等逾時 —— 指令看起來就是死當,毫無訊息。 真相只在 dmesg 裡: 

EXT4-fs (mmcblk0p1): Cannot load crc32c driver.
[ 10.980000] mount_root

extroot 需要模組在 preinit 就位

/lib/libfstools.so 內含字串 /sbin/kmodloader %s/etc/modules-boot.d/ —— mount_root 會自己載入 modules-boot.d 的模組,早於 extroot。 opkg 安裝 kmod 時已自動建好那些 symlink,這層剛好免費過關。 

[  9.860000] mount_root: loading kmods from internal overlay
[ 10.960000] EXT4-fs (mmcblk0p1): mounted filesystem with ordered data mode
[ 10.980000] mount_root: switched to extroot

坑 · 從 Windows 連進去就先摔三次

mDNS 解析優先給 IPv6 假訊號

症狀
ping mylinkit.local → Reply from fe80::9e65:f9ff:fe1d:6a92
原因
mylinkit.local 同時有 A 和 AAAA 記錄,Windows 偏好 IPv6 link-local,你完全看不到 IPv4 位址。
解法
用 ping -4 或 Resolve-DnsName。順帶一提,link-local fe80::9e65:f9ff:fe1d:6a92 是 MAC 9c:65:f9:1d:6a:92 以 EUI-64 推導而來 (9c 翻轉 U/L bit 成 9e,中間插 ff:fe)—— 可用來確認是同一台裝置。

Dropbear 沒有 sftp-server

症狀
ash: /usr/libexec/sftp-server: not found
原因
OpenWrt 用 Dropbear,不提供 SFTP 子系統。而 pscp 預設走 SFTP。
解法
加 -scp 強制舊版 SCP 協定。

plink 的 host key 提示會掛住

症狀
"y`n" | plink … → 永遠不返回
原因
把 y 用管線餵進去並不可靠;而 -batch 遇到未快取的金鑰會直接放棄。
解法
先故意用 -batch 失敗一次,它會把指紋印在錯誤訊息裡;之後每次都明確帶 -hostkey SHA256:…。全程非互動,且不降低安全性。

PowerShell 會吃掉傳給原生程式的雙引號 最耗時

症狀
ash: crc16: not found　/　ash: syntax error: unterminated quoted string
原因
PowerShell 把參數傳給 plink.exe 時會剝掉內嵌的雙引號,於是遠端 ash 看到裸的 | 並當成管線;$ 的跳脫也會被二次解讀。這個坑在整個過程中反覆咬人。
解法
不要在命令列裡塞遠端 shell 腳本。改成 本機寫 .sh → 轉 LF → pscp → plink "sh /tmp/x.sh"。 這個模式已經固化成 provisioning/lib/run-on-board.ps1。

坑 · 2016 年的 OpenWrt,基礎設施都鏽了

opkg update 的簽章驗證已失效

症狀
Signature check failed. Remove wrong Signature file.
原因
Packages.gz 抓得到,但 archive 伺服器的 .sig 對不上韌體內建金鑰,清單被整包丟棄。
解法
不要動 check_signature。改成側載:在 PC 上從 archive.openwrt.org 下載 .ipk,傳到板子後 opkg install /tmp/xxx.ipk —— 本機 ipk 安裝不經過清單簽章檢查。

板子的 busybox wget 沒有 SSL

症狀
wget: can't execute 'openssl': No such file or directory
原因
下載站已強制 https,而 busybox wget 需要外部 openssl helper。(弔詭的是 opkg 自己抓得到,它走不同的 fetcher。)
解法
所有下載都在 PC 端做,再 pscp 推上去。Entware 的 installer 剛好全走 plain http://,所以能直接在板子上跑。

沒有 od、fdisk、blkid

症狀
ash: od: not found　/　ash: fdisk: not found
原因
精簡 busybox。block info 要裝了 block-mount 才有,但那時你正需要它來判斷檔案系統。
解法
用 dd + hexdump 直接讀特徵位元組。MBR 類型位元組在偏移 450;ext 的 magic 53 ef 在分割區偏移 1080,磁碟區標籤在 1144。

kmod 的 vermagic 必須逐字相符

原因
每個 kmod-* 都硬相依 kernel (=3.18.23-1-<md5>)。韌體若是客製 build,官方 feed 的模組就用不了。
解法
先比對再下載。板子:opkg list-installed | grep ^kernel;feed:解開 Packages.gz 看 Depends。本例兩邊都是 32322c69cacfebf6e22f4e61cea9bebc,所以能用。

坑 · 設定寫對了,還是可能悄悄失效

複製 overlay 的時機:先寫 fstab,再複製 我犯過

症狀
重啟後 /etc/config/fstab 是空的(但 extroot 竟然仍生效)
原因
先把 /overlay 複製到 SD,之後才寫 fstab,於是 SD 上那份 upper/ 沒有它。開機仍生效是因為 preinit 讀的是內建 flash 那份。
解法
順序:裝好所有套件 → 寫 fstab → 最後才 tar 複製 overlay。

fstab 有兩份,開機讀的不是你在改的那份 長期陷阱

原因
extroot 的判斷發生在 preinit,那時 SD 還沒掛上,/sbin/block 只能從內建 jffs2(/dev/mtdblock6)的 upper/etc/config/fstab 讀設定。extroot 生效後你看到的 /etc/config/fstab 其實住在 SD 上,改它不影響開機。
解法
要改開機行為,得掛內建那份: 
mkdir -p /tmp/i && mount -t jffs2 /dev/mtdblock6 /tmp/i
vi /tmp/i/upper/etc/config/fstab
umount /tmp/i

mountd 會把 SD 重複掛載一次

症狀
/dev/mmcblk0p1 同時出現在 /overlay 和 /tmp/run/mountd/mmcblk0p1
原因
LinkIt 韌體的 S80mountd 在 extroot 之後才啟動,不知道該裝置已被徵用,於是又掛到 /Media/SD-P1。結果是整個 rootfs 透過 samba 分享出去。它的 uci 設定只有 timeout 和 path,沒有黑名單 —— mmcblk 寫死在二進位檔裡。
解法
/etc/init.d/mountd disable 然後重啟。代價是 USB 磁碟不再自動掛載。另外 stop 殺不掉 daemon,只有 disable + 重啟有效。

坑 · 驗證方法本身 —— 三個自己製造的假訊號

這一節值得單獨列出來。整個過程中,誤導我最久的不是板子,是我自己寫的檢查。

pgrep -f 會比對到自己的命令列 假陽性

症狀
pgrep -f /sbin/mountd → "STILL RUNNING"(其實根本沒在跑)
原因
連中兩次。pgrep -f 比對完整命令列,而執行這個檢查的那條 SSH 命令列本身就含有 /sbin/mountd 字串。同理 ps w | grep mountd 也會撈到名為 disable_mountd.sh 的腳本。
解法
用 pgrep -x、ps w | grep '[m]ountd',或直接讀 /proc/*/exe。最乾淨的是把檢查放進腳本檔,讓命令列裡不出現那個字串。

管線後面的 $? 是 tail 的離開碼

症狀
python3 -m virtualenv … | tail -6 ; echo rc=$? → rc=0(其實 segfault 了)
原因
寫成 cmd | tail 之後再讀 $?,拿到的是管線最後一個指令的結果。真正崩潰的程式被完全掩蓋。
解法
先 cmd >log 2>&1 再讀 $?。並且把訊號翻譯出來:132=SIGILL、138=SIGBUS、139=SIGSEGV。

busybox 靠 argv[0] 決定 applet 害我推翻對的假設

症狀
cp busybox bb_sd; ./bb_sd true → rc=127,看起來像「從 SD 執行會失敗」
原因
busybox 是 multi-call 二進位檔。改了檔名,它就找不到對應 applet 而回 127 —— 那不是崩潰。我拿這個結果去「證偽」了一個其實正確的方向,浪費了一輪。
解法
複製 busybox 做對照時保留檔名,只改目錄。並且永遠區分 rc=127(找不到)與 rc≥128(被訊號殺死)。

Python

為什麼 uv 裝不上去 放棄

這不是設定問題,是根本沒有這個二進位檔。三層都不通:

層事實
官方發行檔uv 0.11.28 的 19 個 asset 涵蓋 aarch64、armv7、i686、ppc64le、riscv64、s390x、x86_64 —— 沒有任何 MIPS 目標
就算有uv 需要 Python ≥ 3.8;板子上是 2.7.9,OpenWrt feed 最高 3.4.3。uv python install 抓的 python-build-standalone 同樣沒有 MIPS build
自己編mipsel-unknown-linux-musl 自 Rust 1.72 起降為 Tier 3,沒有預編譯 std,要 nightly + -Z build-std。另外預期會撞上 MIPS32 缺 64-bit 原子指令、以及 TLS 後端(aws-lc-rs/ring)沒有 MIPS 支援 —— 這兩點未經實測

Entware:唯一可行的現代 Python 路線

Entware 有 mipselsf-k3.4 這個 target —— soft-float mipsel、kernel ≥ 3.4, 正好對上這塊板子。它自帶 glibc 2.27 和自己的 loader /opt/lib/ld.so.1, 跟系統的 uClibc 完全隔離,互不污染。這就是它能在 2016 年韌體上跑 2026 年套件的原因。

它裝在 /opt,而 /opt 現在坐落於 extroot 的 SD 上 —— 沒有先做 extroot,這一步不可能發生(52 MB 的 Python 塞不進原本 9.8 MB 的 flash)。 也正因為它在 SD 上,才踩到了下面那個問題。

⚠ 從 SD 執行的 Entware 二進位檔會隨機崩潰 已有繞道

這是整個過程中最嚴重的發現,而且它不是 Python 的問題。 只要 /opt 底下任何執行檔的頁面被逐出 page cache、必須從 SD 重新 fault 回來, 就會以 SIGILL / SIGSEGV / SIGBUS 崩潰。這台只有 126 MB RAM 而且沒有 swap, 所以驅逐是必然會發生的。

證據

三向對照,每組在 drop_caches 後冷啟動 10 次:

a) loader + libs + exe 全在 SD        ok=0/10   ILL=1 BUS=1 SEGV=2 …
b) 一模一樣的檔案複製到 tmpfs (RAM)   ok=10/10
c) loader 在 RAM,libs + exe 在 SD    ok=0/10
d) busybox from tmpfs                 ok=10/10
e) busybox from flash (squashfs)      ok=10/10

(b) 證明 glibc 和那些二進位檔本身完全沒問題。 而且用 read() 讀同樣的 bytes 是 bit-perfect —— 6.4 MB 的函式庫冷快取 md5 八次、raw 分割區 48 MiB 讀四次,checksum 全部相同。

資料進到記憶體是對的,執行起來卻是垃圾

這是 I-cache 與 DMA 不一致的典型特徵:read() 走 D-cache 拿到正確資料, 而 CPU 執行時從 I-cache 取到的是舊內容。

但我沒有把它證明到 driver 層級,而且有一個結果與這個理論衝突: 420 KB 的 busybox 從同一張 SD 執行,10/10 通過。所以這裡只陳述證據,不宣稱已定位。

已驗證的繞道(2026-07-12)

把 /opt 打包成 squashfs 映像檔放在同一張 SD 上,再 loop-mount。 squashfs 的頁面是 CPU 解壓縮寫進去的,不是 DMA 直接填入被 mmap 的頁面 —— 這剛好解釋了為什麼 flash 上的 squashfs(/rom)從來沒出過事。 實驗結果(與上表同一套冷快取測試法): 

ext4 直讀(對照組)     grep 0/10   python3 0/10
squashfs loop-mount     grep 10/10  python3 10/10
soak 加碼               grep+python3 各 20 次、真實 Python 運算 10 次 → 70/70

同一張卡、同樣的檔案、同樣的逐次 drop_caches —— 唯一的差別是頁面 怎麼進記憶體。細節與腳本在 provisioning/05-squashfs-opt/:kernel 的 squashfs 只編了 xz 解壓(gzip 映像會被拒)、原廠 kernel 連 loop device 都沒有 (側載 kmod-loop+losetup)、mksquashfs 得先搬進 tmpfs 從 RAM 執行(它自己就是會冷快取崩潰的 SD 上 glibc 執行檔)。 開機自動掛載的上線化列在 TODO.md;真正的根治仍是換一版 kernel ≥ 5.x 的現代 OpenWrt。

那現在到底能不能用?

能,但要知道界線。剛開機、記憶體充裕、頁面還在快取裡的時候,Python 完全正常 —— pip install 連得上 PyPI,virtualenv 建得出環境(實測 16 秒,含 seed pip 26.1.2)。 問題出在跑久了、記憶體被別的東西吃掉之後。

所以現階段的務實用法是:把 uv 裝在 PC 上做依賴解析與鎖版, 板子只跑純 Python 程式碼,並且接受它可能需要重試。 在上面那個問題解決之前,不要把 /opt 裡的東西放進開機自動啟動的服務 —— 這也是為什麼 rc.unslung 那段刻意沒有寫進 /etc/rc.local。 2026-07-12 起這條禁令有了出口:squashfs 繞道已實驗證實(見上節,70/70), 等開機自動掛載上線(TODO.md 第一項)之後,這條界線就可以正式解除。

插上 eth0 之後,整個區網(不只板子)在幾秒內動不了,拔線才恢復。 現場證據(br-lan: received packet on eth0 with own address as source address)證實是 L2 迴圈,不是訊號差。開 STP 沒用—— 真正的問題出在 /etc/config/wireless,不在 /etc/config/network。

兩次抓錯真正的橋接成員

uci show network 顯示 network.lan.ifname='eth0 ra0', 看起來迴圈的另一邊是 ra0。跟著這個線索開了 network.lan.stp、等了 36 秒、還即時盯著 port state—— 兩個 port 全程停在 state=3(forwarding),完全沒有收斂跡象。

第二次現場測試 · logread -f

核心自己說出真相

全程開著 logread -f 監控,重連 eth0 的 36 秒內, net_ratelimit 每 5 秒把 400–1000+ 筆重複警告壓下去, 而且數字是往上走的——風暴在惡化,不是還沒收斂完。 

br-lan: received packet on eth0 with own address as source address
/sys/class/net/br-lan/brif/

直接讀 sysfs,而不是相信 UCI 設定檔

真正的 bridge 成員清單跟 network.lan.ifname 寫的完全不一樣: 是 eth0 + apcli0,沒有 ra0。 無線介面的 network 歸屬是在 /etc/config/wireless 裡另外指定的 (option network),不會反映在 /etc/config/network 的 ifname 清單裡——這是 OpenWrt 本來的機制,不是設定寫錯。 

config wifi-iface 'sta'
    option ifname 'apcli0'
    option network 'lan'   ← 就是這行,不在 network.lan.ifname 裡
修復

把 apcli0 搬到已經存在、卻沒人用的 wan

板子上本來就有一個設好 NAT(option masq '1')、 forwarding 也只允許 lan → wan 單向的 wan network,只是沒有任何裝置掛在上面。把 wireless.sta.network 從 lan 改成 wan,apcli0 從 br-lan 消失, 迴圈在結構上斷開。改完當下 SSH(走 apcli0)斷線是預期行為, 插回 eth0 即可從 lan 重新連上。 

uci set wireless.sta.network=wan
uci commit wireless
wifi reload
驗證

9 分鐘沒有新紀錄

插回 eth0 瞬間仍有 13 秒殘留警告(舊 ARP/MAC 快取的過渡效應), 之後 date 跟最後一筆警告時間戳相差近 9 分鐘、沒有再出現—— 跟前兩次「STP 開著也持續惡化」的樣子完全不同,這次是真的停了。

為什麼開 STP 完全沒用

STP 只能防「兩個都懂 STP 的 bridge」之間的迴圈

802.1D 的迴圈偵測,靠的是所有參與的 bridge 互相交換 BPDU 封包來協商拓樸、 決定哪個 port 該進入 blocking。這裡的迴圈是繞經一般家用路由器 才接起來的——路由器不懂、也不會轉發 BPDU。對板子自己的 bridge 而言, eth0 跟 apcli0 就是兩條各自獨立、通往不相關網路的線, 它沒有任何機制能發現這兩條線其實在外面被接在一起。開 stp、 等多久都一樣,不是時間或運氣的問題——這個迴圈的形狀從根本上就不在 STP 能處理的範圍內。真正能處理這種「繞經外部裝置接回來」的迴圈,只能從拓樸 本身下手:把其中一條路徑改成路由(NAT),而不是繼續橋接。

坑 · Go 與 MCP 協定之間

Go 的 []byte 在 JSON 裡是字串,不是陣列

症狀
client 送 [1, 2, 3] 被 schema 驗證拒絕;工具 schema 裡該欄位是 string
原因
encoding/json 把 []byte 一律編成 base64 字串,MCP SDK 產生的 schema 也跟著變成 string——跟「位元組陣列」的直覺完全對不上。
解法
所有 raw-byte 欄位改用 []int(逐一驗證 0–255)。唯一例外是 i2s_play 的音訊 payload:檔案夠大,base64 字串反而遠比 JSON 整數陣列省,留著。

GPIO export 的併發競爭

原因
每個 MCP session 是獨立的 OS process,兩個 session 可能同時對同一支還沒 export 的腳位動手。先 stat 再寫是教科書級的 TOCTOU。
解法
不檢查,永遠直接寫 /sys/class/gpio/export,讓核心去序列化:撞到 EBUSY 就代表別人已經 export 完了,視為成功。

部署了新版,session 還在跟舊 process 講話

症狀
deploy.ps1 成功,新工具卻沒出現;修掉的 bug 看起來還在
原因
MCP client 在 session 開始時 spawn 的舊 process 還活著;換掉磁碟上的執行檔不影響它。
解法
重載/重連 MCP session。先確認這件事,再去懷疑 deploy 失敗。

⚠ I2S 錄音:確認是死巷,不是還沒做 死巷

播放沒問題(i2s_play,WAV,實測呼叫成功)。錄音是另一回事: arecord 一啟動就卡死,而且卡住的 process 連 SIGKILL 都殺不掉,只能重開機清掉。

該試的都試了

codec(WM8960)的 capture 路徑確認有上電、路由確認正確;之後又試了把 ALSA buffer/period 加大——同樣的卡死,一模一樣的症狀。這是 2016 年驅動層的 bug,不是設定問題。官方 100 頁的 Developer's Guide 從頭到尾沒提過錄音; 真正的驅動原始碼鎖在一份從沒簽過的 NDA 後面。結論: 這塊板子的錄音就是不可用,任何「說不定這次會動」的嘗試 只會換來一次重開機。完整調查在 docs/superpowers/specs/2026-07-11-i2s-design.md。

MT7688 完全沒有類比輸入,但板上還睡著第二顆晶片:ATmega32U4(Arduino 相容, 8 MHz / 3.3V)。四個階段把它接進 MCP:工具鏈打通(交叉編譯 + ISP 燒錄)→ 選定 Firmata 子集當線上協定 → ATmega 韌體 → MT7688 側 decoder + 兩支新工具 (atmega_adc_read、atmega_bridge_raw)。 每一階段都在真實硬體上驗證過,包括直接解讀 Firmata 原始位元組的 round-trip。

橋接的 UART 在 Linux 側是 /dev/ttyS0——這不是刪去法猜的,是從 dmesg 的 pinmux 紀錄(pin 12/13 → uart0 → 10000c00.uartlite → ttyS0)一路對出來的。板上共三個 UART:ttyS0 橋接、ttyS1 給 uart_transact、 ttyS2 是 console——搞混任何兩個,東西就是不會動。

症狀

avrdude:AVR device not responding

原因
ATmega 有自己獨立的 USB 電源孔(絲印 "USB Power & MCU USB Port"),不從 MT7688 側取電。沒插它,目標晶片整顆沒電,ISP 當然敲不通。查過的文件全都沒寫,是請人對著實體板檢查才發現的。
解法
插上那個孔。avrdude 隨即讀到真實裝置簽章 0x1e9587。之後再遇到 "not responding",先檢查這條線,再懷疑別的。

/tmp 是 tmpfs,而且會被悄悄清掉

症狀
run-avrdude /tmp/blink.hex → No such file or directory(明明剛 scp 上去)
原因
板子的原廠韌體似乎會定期清 /tmp;電源 troubleshooting 拖了幾分鐘,檔案就沒了。
解法
scp 完立刻燒錄,兩步之間不要停。

沒有 checksum 的 UART,得自己防位元翻轉

原因
Firmata 把 14-bit 數值拆成兩個 7-bit 資料位元組傳,線上沒有任何 checksum。decoder 若不遮罩,一個翻轉的 bit 7 就能變出超出 0–1023 的假讀值。
解法
decode 前一律 & 0x7F,附迴歸測試。code review 抓到的。

成功路徑上被靜默吞掉的錯誤 code review 抓到

原因
atmega_adc_read 讀到值之後要把 REPORT_ANALOG 關掉;舊版在這一步失敗時直接回傳 (value, nil)——通道卡在啟用狀態,呼叫端毫無跡象,下一次呼叫才莫名其妙。
解法
重排尾端邏輯:關閉失敗一定浮出錯誤(訊息帶上已讀到的值);逾時錯誤永遠優先於後續的關閉失敗。

已修 · 黑名單裡記錯腳位的「ISP reset」 2026-07-12 修正

板上的 /etc/avrdude.conf 和 Developer's Guide 的 pin-out 圖都說 ISP reset 線是 GPIO 3;黑名單裡標「ATmega ISP reset」的卻是 pin 38。pin 3 一度只是恰好因為 I2S(0–3 整段)被擋住—— 哪天有人覺得「我不用音訊,pin 3 解鎖沒差」,就會在韌體運作中把 ATmega 重置。

實地查證後真相:pin 38 其實是 Wi-Fi Reset 按鈕

/sys/kernel/debug/gpio 顯示 gpio-38 被 kernel 以輸入腳持有, 對應 device tree 的 gpio-keys-polled/wps 節點(label "reset"、 linux,code = KEY_WPS_BUTTON)——它是板上的 Wi-Fi Reset 按鈕, 跟 ATmega 毫無關係;當初「ATmega ISP reset」是從 pinmux 群組名間接猜的。 修正:pin 3 的封鎖理由現在同時寫明兩個角色(I2S + ATmega ISP reset), pin 38 維持封鎖、改用正確理由;措辭由迴歸測試 TestCheckBlocked_ResetPinReasons 鎖住,並對部署後的 server 實機驗證過兩支腳位回傳的錯誤訊息。
