# MCP server: I2S playback tool — design

Status: approved, not yet implemented
Date: 2026-07-11

## Context

`mt7688-mcp-server` currently exposes 10 tools: GPIO, I2C, SPI, PWM, and
UART (`uart_transact`) — all shipped (see the SPI/PWM and UART design
docs). Those specs' roadmaps deferred I2S because its tool-shape question
is fundamentally different from every prior tool: I2S is a continuous
audio stream, not a register read/write, so "what does an MCP call for
this even look like" had to be answered before any bus-level design made
sense.

User-set order for remaining hardware coverage: UART (done) → **I2S
(this spec)** → ATmega UART bridge → ADC.

## Live findings, 2026-07-11 — this is not raw I2S register work

Unlike every prior tool, this board already has a **complete, working ALSA
sound system** on top of the I2S peripheral — confirmed directly on the
real board before any design work:

- `/proc/asound/cards` shows card 0, `MTK APSoC I2S`, driving a **WM8960
  codec** (I2C address `0x1a`) via the machine's I2S link. `/dev/snd/`
  has both a playback (`pcmC0D0p`) and capture (`pcmC0D0c`) device.
  `aplay`/`arecord`/`amixer` (ALSA userspace tools, v1.0.28) are already
  installed.
- `aplay -D hw:0,0 --dump-hw-params` successfully negotiates with the
  hardware: `FORMAT: S16_LE` only, `CHANNELS: [1 2]`, `RATE: [8000
  48000]`.
- This means the design question isn't "how do we drive the I2S
  peripheral's registers" (that's already solved, by a kernel driver) —
  it's "what should an MCP tool built on top of the existing ALSA stack
  look like."

## Investigation: capture (recording) is broken at the driver level

Before finalizing scope, playback and capture were both tested for real
(not just hw_params negotiation) directly on the board. The results
diverged sharply enough to change the plan mid-brainstorm:

- **Playback works end-to-end.** A real 1-second WAV (not just a
  negotiation probe) played via `aplay -D hw:0,0` to completion, exit
  code 0. `dmesg` showed several `XRUN` (buffer underrun) messages during
  playback — a real, if minor, audio-quality caveat (possible clicks/
  glitches) — but the process completed normally and the device was
  usable again afterward.
- **Capture reliably wedges the board.** Three separate `arecord`
  attempts — `plug:default` with `IMA_ADPCM`, `plug:default` with
  `S16_LE`, and `hw:0,0` directly with `S16_LE` — **all hung**, every
  time immediately after `dmesg` printed a `############## MMAP
  ##############` line (a vendor debug banner, almost certainly from the
  custom `snd_soc_mt76xx_pcm` driver's DMA-trigger path). Once hung, the
  `arecord` process became unkillable even with `SIGKILL` — `ps` showed
  it collapse into a bracketed `[arecord]` kernel-thread-style entry with
  zero memory, consistent with being stuck in an uninterruptible kernel
  wait (most likely blocked forever on a DMA-completion interrupt that
  never arrives for the capture direction). Each hang required a full
  board reboot to clear; no non-destructive recovery was found (the
  relevant driver modules are loaded — `snd_soc_wm8960`,
  `snd_soc_mt76xx_pcm`, `snd_soc_mt76xx_i2s_ctl`, etc. — but unloading
  them while a process holds the device open was not attempted, given low
  confidence a vendor BSP module would cleanly `rmmod`/`insmod` on a live
  board and the cost of getting that wrong is another wedge).

This is the same category of finding as the pre-existing, documented
Entware/tmpfs SIGILL bug in `dev-notes.html`: a real, reproducible bug in
vendor-supplied driver code, not something fixable by changing how this
project's own code calls into it, and not worth chasing to full root
cause (no driver source, no realistic way to patch/rebuild it, repeated
reproduction costs a board reboot each time).

**Decision: this spec covers playback only.** `i2s_record` is explicitly
out of scope — not deferred because of low priority, but because the
underlying capture path is confirmed broken at the driver level. If this
ever gets revisited, treat "why does capture hang" as its own
investigation, not an extension of this spec.

## Goals (v1.3)

- Expose one tool, `i2s_play`, that plays a caller-supplied WAV clip
  through the board's speaker/headphone output and blocks until playback
  finishes.
- Do this by shelling out to the already-proven-working `aplay` binary,
  not by reimplementing ALSA PCM programming in Go.

## Non-goals (v1.3)

- **Recording (`i2s_record`).** Confirmed broken at the driver level (see
  above). Not implemented. Documented here so it doesn't get silently
  reproposed without this context.
- I2S register-level control, ALSA mixer/volume control (`amixer`-style
  tools), format conversion, or anything beyond "play this WAV clip." Can
  be added later as separate, narrower tools if a real need shows up —
  YAGNI for v1.3.
- Automatic format/sample-rate conversion. Playback targets `hw:0,0`
  directly (not `plug:`-wrapped), matching what was actually tested. A
  WAV outside the hardware's native capability (not `S16_LE`, not 1-2
  channels, not 8000-48000 Hz) fails with `aplay`'s own clear error
  rather than being silently resampled — consistent with this project's
  existing "raw primitive, don't paper over what the hardware actually
  supports" posture.
- Non-WAV formats (MP3, FLAC, Ogg, etc.). Investigated and rejected for
  this round: no codec encoder/decoder is installed, and `opkg update`
  reaches the archived OpenWrt 15.05.1 package feed but **fails signature
  verification** — installing new packages isn't currently possible
  without downgrading security posture (`--no-signature-check`), which
  wasn't attempted and isn't recommended without a separate, explicit
  decision. `arecord`'s own `IMA_ADPCM`-to-WAV writer was also tried and
  found unsupported by this alsa-utils build ("Wave doesn't support
  IMA_ADPCM format") — moot now that recording is out of scope, but
  recorded here in case compressed-audio work is revisited later.

## Tool surface (v1.3)

| Tool | Signature | Notes |
|---|---|---|
| `i2s_play` | `(wav_base64 string) -> {ok: bool}` | Blocks until playback completes. Fixed to `hw:0,0`. WAV format is self-describing (RIFF/fmt chunk carries sample rate/channels/bit depth), so no separate parameters are needed — `aplay` reads them from the file itself. |

## Why base64, not a `[]int` sample array

Every prior tool with binary payloads (`i2c_read`/`write`, `spi_transfer`,
`uart_transact`) uses `[]int` (one JSON array element per byte), following
the standing rule that `[]byte` breaks the MCP SDK's schema (see the
2026-07-10 spec's "Live verification" section). That rule is about
avoiding a `[]byte`-vs-JSON-array **type** mismatch — it doesn't mean
every binary payload must be a numeric array. For audio, a `[]int`
sample array would be dramatically less token-efficient than a base64
string for the same bytes: a JSON array renders each byte as its own
comma-separated decimal literal (often 4-5 characters per byte once you
count the digits and the comma), while base64 renders 3 bytes as 4
characters. Given audio payloads are already the largest data this server
handles (see the size cap below), the encoding choice has a real,
measurable effect on how much of an LLM's context one `i2s_play` call
costs — base64 is the standard, appropriate choice here, declared
honestly as a `string` field (not a mistyped `[]byte` pretending to be an
array).

## Payload size cap — recalibrated mid-design

An initial proposal of a 2MB raw-WAV cap (matching a rough symmetry with
what a hypothetical recording duration cap would have implied) was
**wrong by roughly 20x** once actually converted to LLM token cost: base64
is high-entropy, incompressible data from a tokenizer's perspective,
averaging roughly 3-4 characters per token. 1MB of raw WAV becomes ~1.4M
base64 characters — on the order of 300,000-450,000 tokens, large enough
to exhaust most context windows on its own. Recalibrated cap: **100,000
bytes (100KB) of decoded WAV**, roughly 133KB of base64 text, on the
order of 30,000-45,000 tokens — still substantial, but a clip a caller
could actually afford to send (roughly 6 seconds at 8kHz mono, less at
higher quality/channel settings). This bound is validated on the decoded
byte length, after base64-decoding the input and before invoking `aplay`.

## Validation

- Base64 decoding: if `wav_base64` doesn't decode as valid base64, reject
  with a clear error before touching the audio device.
- Size: decoded length must be `1`-`100000` bytes.
- Format sanity check: decoded bytes must start with the WAV/RIFF magic
  (`RIFF` at offset 0, `WAVE` at offset 8) — a cheap check that rejects
  obviously-wrong input (e.g. a caller accidentally base64ing something
  that isn't audio at all) before spawning a subprocess. Deeper format
  validation (sample rate, channel count, bit depth) is intentionally left
  to `aplay` itself — duplicating a WAV parser in Go to pre-validate what
  `aplay` will validate anyway is unnecessary work for a clear error
  message that already comes from `aplay`'s own stderr.

## Implementation approach

`exec.CommandContext(ctx, "aplay", "-D", "hw:0,0", "-q")`, with the
decoded WAV bytes piped to the subprocess's stdin (`cmd.Stdin =
bytes.NewReader(decoded)`) and stderr captured for error reporting. This
is the **first tool in this server that spawns a subprocess** rather than
doing direct syscall/ioctl/sysfs work — a real architectural departure
from every prior tool, called out explicitly rather than introduced
quietly. It's the pragmatic choice here specifically because:

1. `aplay` is already proven to work end-to-end on this exact hardware
   (see "Investigation" above) — reimplementing ALSA PCM programming
   (`hw_params`/`sw_params`/buffer management, all ioctl-driven, with no
   `x/sys/unix` built-in support the way termios had) would be
   substantially riskier and more work for no real benefit.
2. `CGO_ENABLED=0` static linking is a load-bearing, established
   constraint for this project (avoids the original SIGILL bug class,
   avoids needing the OpenWrt SDK toolchain) — ruling out linking against
   `libasound` via cgo.

A generous process-level timeout (`context.WithTimeout`, ~30 seconds —
comfortably above the ~6.25-second worst-case duration implied by the
100KB cap at the lowest supported bitrate) guards against `aplay` hanging.
**Caveat, stated honestly rather than glossed over:** the capture-path
investigation above found that when this vendor's driver actually hangs,
the resulting process is `SIGKILL`-resistant — a Go-level
`context.CancelFunc` plus `cmd.Process.Kill()` will not necessarily free
a device wedged by a real driver-level DMA hang, the way it would for an
ordinary hung subprocess. Playback was not observed to hang in testing
(only capture was), so this is a residual, undemonstrated risk for
playback specifically, not a known bug — but if it ever happens, the fix
is a board reboot, not a smarter timeout.

## Safety: GPIO blocklist extension

Add to `blockedPins` in `blocklist.go`:

- `0`, `1`, `2`, `3` — I2S (`i2s` pinmux group, WM8960 codec)

Same rationale as every prior extension: a `gpio_write`/`gpio_set_direction`
on these pins wouldn't error today, it would just risk interfering with
the audio codec's I2S signaling once `i2s_play` (and the kernel's own
audio driver) are using them.

## Error handling

- Validation errors (bad base64, size out of range, missing WAV magic):
  rejected before any subprocess is spawned.
- `aplay` non-zero exit: surfaced with its captured stderr, so a real
  hardware/format error (e.g. an unsupported sample rate) reaches the
  caller with `aplay`'s own diagnostic, not a generic failure.
- Context-deadline-exceeded (the 30s safety net triggered): surfaced
  clearly as a timeout, with the caveat above about what that does and
  doesn't guarantee about device state afterward.

## Source layout

- `i2s.go` — platform-independent validation (base64 decode, size bound,
  WAV magic check) and the `PlayI2S` wrapper. No platform split needed
  here (unlike SPI/UART) — spawning a subprocess via `os/exec` is
  portable Go, no `//go:build linux`-gated syscalls required. On a
  non-linux dev machine, `PlayI2S` will simply fail when `aplay` isn't
  found on `PATH` (a clear, natural error — no stub file needed, unlike
  the ioctl-based tools where a missing platform implementation had to be
  explicitly stubbed).
- `i2s_test.go` — validation-only unit tests, no hardware or `aplay`
  needed.

`main.go` gains one new `mcp.AddTool` registration.

## Build & deploy

No changes — same `build.ps1`/`deploy.ps1`. Nothing new to cross-compile
(`os/exec` is portable); the only new runtime dependency is `aplay`
already being present on the board, which is already confirmed true.

## Testing

- Validation logic: plain `go test`, no hardware needed.
- Actual playback: can't be meaningfully tested off the hardware. Manual
  verification against the real board after deploy — this time with a
  real, audible expectation (the design doc for every prior tool could
  only verify "no error" or "round-trips correctly"; audio is the first
  tool where a human listening is part of what "verified" means).

## Open questions for implementation

- None deferred to implementation time for this spec — unlike UART's
  termios API question, `os/exec` and `encoding/base64` are standard
  library, fully portable, nothing platform-specific to verify against
  real source before writing code.

Resolved during design: playback-only scope (capture confirmed broken at
driver level), subprocess-based implementation (not raw ALSA ioctl, not
cgo), base64 encoding (not `[]int`), 100KB payload cap (corrected from an
initial, token-cost-miscalibrated 2MB estimate), `hw:0,0` direct device
targeting (not `plug:`-wrapped, matching what was actually tested).
